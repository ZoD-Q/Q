# 钱包支付真实工作区

`/q-admin/wallet-payments` 是独立于平台演示的支付操作员入口。本文记录接口实现和隔离环境的验收结果；发布步骤见 [上线与验收手册](../../backend/deploy/WALLET-CLOSURE-2026-11-06.md)。

## 身份与网络

- 复用 Q `POST /v1/auth/login`，成功后必须 `GET /v1/payments/operator/me`，校验返回用户与登录用户一致及 maker/checker 角色。没有第二套管理员账户，不使用原演示署名切换权限。
- Bearer 只存在内存。密码提交后立即清空；退出、切号、401和组件卸载隔离在途请求与迟到响应，退出尝试撤销原Q会话。pagehide 同步失效 API 与代次，再用 flushSync 清受保护子树；pageshow(persisted) 再次清理，浏览器后退不能恢复旧凭证或表单。
- 真实凭据入口仅在 `https://q.kaicloudpay.com` 精确官方 origin 开放；裸IP或其他地址只提供官方安全链接，不显示密码框。只有 `VITE_Q_LOCAL_API_TEST=1` 且页面自身位于 localhost/127.0.0.1/::1，才接受 `VITE_Q_API_URL` 指定的loopback API。生产构建强制清除本地验收开关与地址。
- 每次请求15秒上限、AbortController、响应大小上限、拒绝重定向、omit cookies，无自动重试。所有出口 finally abort；超限 reader 取消不等待不受信任的 cancel promise，提前拒绝不遗留无限流。错误只显示白名单状态，不回显服务端原文、SQL、令牌或凭据。

## 写入与恢复

写入前显示目标、金额、版本/摘要并要求确认。初审与复审分离，付款人不能审批自己的订单；客户端禁用理由只是帮助说明，最终约束由后端强制。

结果不明（网络、取消、5xx、成功响应损坏或401）保留原请求。待确认动作按规范化 API origin（含协议、端口）和服务端 user_id 双重隔离；先 GET 原记录，确认身份、版本及状态后才清除。只有当前会话仍持有原载荷时才允许明确重试同一请求，不创建新 key。

本机使用 v2 恢复信封，校验来源、账号以及每个操作的必要 ID、版本和摘要。密码、令牌、原因正文、银行原文件和映射内容不持久化。刷新、退出、切号或 401 后清除实例拥有的原文件、备注与可重试载荷，重新登录仅可按最小引用查询恢复；不宣称对 JavaScript 字符串作物理内存擦除。

同一来源与账号的存储更新通过 Web Locks 串行读、合并，并按完整请求身份比较后才清除，防止多标签页覆盖。来源不符、引用损坏、无法保存或浏览器不支持锁时拒绝新写入。无来源的旧 v1 记录不自动迁移或删除，需运维核对。每个作用域最多 40 条待核引用。

## 功能

- 五个订单队列：待核实、初审、复审、已入账、差异；分页、按订单ID查询、完整金额和证据版本、初审复审及审计信息。
- 完整原单退款：申请、另一复审人批准、外部退款证据上传、退回补正、摘要复核、结果未知登记；原材料历史分页并按版本下载，补正不再执行外部退款、不释放冻结，旧哈希不能核验新版本。不调用付款渠道。
- 结算导入：规范化JSON≤128KiB/200行，与原始PDF/CSV≤256KiB同时上传。支付和退款行可共存；退款负总额及 signed 手续费、净额精确合计，银行金额可为零或负。HKD储备仍要求正金额、空rows。原材料重核追加 check_version 与不可变计算历史，零差异后先刷新再独立核材，未知重核只 GET 恢复。
- 汇率状态：参考价、时效、暂停/过期/预警、候选及服务端代次；仅明确允许的候选可经人工核对后激活，参考报价不代表实际兑换。

## 合同与集成

PaymentOrder、PaymentOperatorMe/OrderSummary/Detail、Refund、Settlement和FxStatus均复用已统一生成的 `mobile/shared/src/generated.ts`；运行时边界校验集中在 `web/src/payments/types.ts`，没有手改共享生成文件。结算未知导入读取 `GET /v1/payments/operator/settlements/by-client-key/{key}`，不依赖第一页列表。

`web/deploy/deploy_tools.py` 仅为 `/q-admin/wallet-payments` 文档提供 `connect-src 'self'` 和 `Cache-Control: no-store`，其余演示页面仍禁止业务连接。两个工作区以完整文档导航切换。上线需要配置官方域名同源入口并更新服务器可信发布辅助程序。

`operator_verified` 表示操作员已核实材料。渠道实账、外部退款执行和银行清算各自需要实际凭证验收。

## 退款写入与恢复的核对项

提交后先核对原请求号、订单、退款编号、操作人、原金额、版本和对应动作结果，再清除待确认引用。上传凭证时同时核对原摘要、外部流水和执行时间。只读恢复先核对退款金额和订单范围，金额不符时保留原引用。

登记未知结果需要原批准人和发起人一致，操作者属于原参与人，且退款版本前进。复核凭证需要原摘要与原凭证版本同时匹配。两个补正版本使用同一份文件时，另一版本仍不能确认旧请求。原人员和版本仅用于恢复引用，不进入 POST 载荷。旧引用缺字段时保持待核。凭证退回继续按历史版本核对。

受控浏览器回归覆盖错请求号、退款编号、状态、金额、人员和证据，以及刷新后恢复和同摘要不同版本。最终版本还通过隔离 Rust API 重跑了原发起人补正与原复审人核验。
