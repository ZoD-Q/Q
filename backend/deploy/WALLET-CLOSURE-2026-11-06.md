# 钱包闭环与公共新闻上线顺序

本次候选以两端已审核且同树的 main 为基线。部署仍以人工合入 `main` 后的实际提交及其通过的流水线制品为准。源码、隔离测试和本地页面都不是线上发布记录。

1. **备份并核对版本。** 核对已运行版本、数据库和迁移清单；保留升级前数据库与受保护配置备份。新增迁移 `2026110501`、`2026110502`、`2026110503`，原9项的内容和校验和保持不变。升级测试在独立 PG 中保留了旧付款证据、审批、入账分录和余额。升级后旧程序不认识新迁移；禁止删除 SQLx 记录或在已接收新资金后用旧库覆盖新账本。
2. **先更新 API，再更新支付后台。** 从已审核的主线制品部署后端，保持原商户、两角色、1%及 HKD10–50,000。启动同步操作员代次，旧过程不能继续用旧权限写。服务健康后确认普通客户读不到操作员数据，检查一个已存在原单的恢复，并核对 12 项成功迁移。旧客户端要更新才能完整展示退款、冻结与负分录。
3. **核对并开启自动汇率。** 仅在新代码和 Compose 转发生效后设置 `Q_PAYMENT_FX_AUTO_REFRESH=1`；核对操作员状态的 `mode=automatic`、真实 ECB 日期、可追溯哈希和 `evidence_verified=true`。普通刷新保留旧报价，已创建订单永久冻结。过期时暂停新报价；来源异常时用候选复核处理，不能通过更改旧时间戳续期。24h/6h、过期与持有状态在操作员页面和服务日志可观察；外部告警通道另行验证。实际观察下一次自动激活后，才记为持续刷新通过。
4. **部署同一主线的 Web 制品。** 先按[受信接收器安装流程](gitlab-cd.md)用经审核源码升级服务器 `/usr/local/lib/q-ci/web/deploy_tools.py`。接收器使用服务器上已安装的辅助脚本，不会从上传的制品执行它，也不会仅随 Web 制品更新自动升级。旧脚本仍会生成阻断钱包请求的 `connect-src 'none'`。用[专属域名配置](nginx-q-domain.conf)在官方域名的两个 Q 虚拟主机复用已部署的管理站点 HTTPS snippet。保留现有图库等运维路由，只增补管理入口及 HTTP 的受信来源门禁；先备份、验证 Nginx 配置，再重载。核对官方 `https://q.kaicloudpay.com/q-admin/wallet-payments` 的版本、真实 Q 登录、`connect-src`、附件下载和窄屏。裸 IP 保留演示入口，真实钱包登录使用官方同源，不扩大 CORS。回环地址只用于显式隔离验收。
5. **验证新闻源状态。** 在实际新服务读 `/v1/market-data/news?topic=central_banks`，检查两个官方来源、缓存时间、文章日期和原文。市场/科技/加密仍分别检查 GDELT 的实际 JSON；没有有效上游记录就显示真实不可用或有时间的旧缓存。央行动态可用并不表示全球覆盖恢复。

隔离验收使用回环供应商与固定标记的新闻样本，未付款、未请求真实退款或换汇。真实资金验收在发布后单独运行：微信、支付宝各一笔到账 HKD10，由付款人确认付款、两个不同且与付款人不同的操作员分别审核，检查每单只入账一次、原订单可恢复。退款由有权人员在官方渠道原路执行；Q 保留双审、冻结、补正与一次冲正。随后用渠道结算原件和银行流水核对首批净额，单列 HKD 储备或真实兑换凭证。没有实际外部证据时，只能记录软件链路与材料复核通过。
