## 发布顺序

1. 将本次变更提交、推送 Mandow，查看最新提交的真实 CI 结果；通过后提交或更新面向 main 的 MR，由人工审核合并。不自动合并或启用自动合并。
2. 从已审核 main 制作同提交发布包。执行前持有 `/run/lock/q-ci-deploy.lock`，备份数据库与持久密钥，在独立恢复库演练新迁移 `2026102001_public_beta_accounts.sql`；保留现有数据库、发布目录和网络。
3. 升级经过审核的 CI 接收器、可信部署模板及配套脚本。接收器在服务器使用既有 root 管理的模板；仅把新 Compose 文件放进发布包不会更新这些模板。新发布包可包含经架构和摘要验证的 `account-admin`，安装权限为 `0555`，维护容器只读挂载，不增加公开管理 HTTP 接口。
4. 重新核对现有 `q_application` 网络、桥接地址及地址占用。2026-10-20 只读观察为 `172.29.0.0/16`、宿主桥接 `.1`、网关 `.3`、API `.2`；这些是观察值，部署前必须复核。不要重建网络或扩大为信任整个私网。设置 `Q_GATEWAY_APPLICATION_IP`，在 root 管理的 `/etc/q/trusted-host-proxies/host.conf` 写入已核验的精确宿主地址，目录只读挂入网关。Rust 只信任已固定的网关地址。
5. 部署新 API 后核对迁移、实际源码/二进制、健康、既有账号和数据；在隔离验收链路验证客户端限流分桶、防伪造头及网关重建后的地址一致性。现有公网服务只做明确授权的功能验收，不使用业务库执行注册压测。
6. 将审核后的 `web/public/privacy.html` 安装为 `/var/www/q/legal/privacy.html`，更新 [Q 专属入口](nginx-q-domain.conf)。页面内联脚本与两处 CSP 哈希必须一致，先 `nginx -t` 再重载；验证公网 HTTPS `/privacy` 内容和响应头，并确认其他虚拟主机保持可用。
7. 完成剩余原生验收，解锁后上传构建 2，确认 Apple `VALID`；将构建加入外部组，提交 Beta 审核。后端、隐私页及 Apple 审核均通过后才启用 100 人公开链接。不得将构建 1 的处理结果当作构建 2 的审核结果。

## 维护、数据与恢复

`account-admin` 使用已有获授权的 SSH/数据库运维边界，不创建新的公众管理员身份。`reports` 默认只读元数据，支持 `--after` 分页；`report UUID --include-content` 才明确读取仍在保留期内的原因和证据。输出可能含私有内容，不进入 CI 或常规日志。维护容器关闭 Docker 日志。

`suspend`、`reinstate`、`delete`、`resolve-report` 需要 `Q_ACCOUNT_ADMIN_MUTATIONS=1` 和重复目标 UUID 的 `--confirm`。Compose 默认值为 `0`；不得为省事长期启用。处理举报需要实际值守，代码存在不等于已承诺或完成审核时效。

删除保留去标识化身份、不可变模拟账本及原交易备注、必要恢复收据；他人举报和已复制内容不随删除全部消失。自动同机备份保留约 14 天，手工和异地副本须另行处理，不能承诺所有副本即时擦除。恢复旧备份后，必须补齐恢复点后的删除及停用状态、重新清理相应数据并验证，再对外提供服务。

执行新迁移后，禁止直接切回忽略账号状态的旧 API。先验证兼容性和删除状态，优先修复前进；恢复数据库必须明确恢复点、停写及损失范围，并保留当前库。持续异地备份、外部告警、真实第三方授权、供应商实账和 100 人容量验收尚未完成。
