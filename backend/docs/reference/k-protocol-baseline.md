# 做插件前必读（给 GPT）：K Protocol 开发规范版

> 规范依据：用户于 2026 年 10 月 15 日提供的《基于 MCP 的开放 Agent 插件协议》文本。
>
> 本文将该文本整理为 GPT 开发前的工作约束与验收清单。“必须”表示必要要求，“应”表示推荐要求，“可以”表示可选能力；不得降低原文要求，或把工程建议扩写为新的 K 协议。

**默认任务是开发并自行发布一个符合 K Protocol 的 MCP 服务，由 KAI Ask（小 K）发现、添加和调用。开发者不需要开发者账号、Registry 注册或人工上架审核。**

本文不代表某个现有宿主或服务已经实现全部规范。具体实施范围以用户当前任务为准；已有授权用于相应工作，不因阅读本文自动扩大为修改宿主、发布服务或执行真实业务的授权。

## 1. 角色与开发范围

| 角色 | 职责 |
| --- | --- |
| 开发者／插件服务方 | 自行控制插件地址、服务实现和用户关系；发布发现信息、MCP 服务及需要的交互界面；维护业务逻辑和服务端权限 |
| KAI Ask／小 K | 作为协议宿主和搜索入口，实现发现、添加、MCP Client、MCP Apps 宿主、用户连接管理与目录索引 |
| 上游业务系统／第三方平台 | 在实际需要时提供数据或业务 API，其可用性与权限须独立确认 |

```text
用户提供域名、HTTPS 链接或二维码
  ↓
KAI Ask 解析 Catalog / Server Card，展示实际来源
  ↓
用户确认添加，通过结构与来源校验后保存服务记录和用户连接
  ↓
KAI Ask 完成实时发现及必要的用户授权
  ↓
MCP Client 调用开发者维护的 MCP Server
  ↓
自己的业务系统 / 已获授权的第三方 API / 直接实现的业务能力
```

开发插件默认不要求修改小 K 的主应用代码。宿主必须具备的协议能力由宿主侧负责；若实际宿主尚未实现，应列为宿主兼容性缺口，不能通过插件自造协议绕过。

用户明确要求的宿主开发可以作为独立工作推进。不要把宿主的搜索、抓取和沙箱职责全部塞进插件服务，也不要把插件开发擅自扩大为重做小 K。

## 2. 固定技术基线，不另造协议

| 范围 | 本规范选定的基线 |
| --- | --- |
| 远程能力调用 | MCP `2026-07-28` |
| 远程传输 | HTTPS Streamable HTTP |
| 对话内交互界面 | MCP Apps `2026-01-26` |
| 连接前服务描述 | MCP Server Card v1 |
| 连接前服务目录 | AI Catalog `1.0` |

三层职责必须保持清晰：

- **Catalog：有哪些服务。**
- **Card：如何连接。**
- **MCP：当前可以执行什么。**

K 不定义独立 RPC 方法、固定业务工具名称、额外消息封装或 UI 描述语言。不要增加通用的“K 调用接口”“K 事件接口”或“K 组件协议”来替代选定标准。

按所提供原文的状态说明：Server Cards 的 SEP 已标记为 Final，发现文档及 AI Catalog 仍有草案标记。K 将其作为选定的发现格式，**不能把它们统称为 MCP 核心规范**。开发遵循上述版本，不用其他版本的示例只替换日期。

## 3. 插件发布与连接前发现

### 3.1 每个插件必须有独立、稳定的 Server Card URL

Card 的响应类型必须为：

```text
application/mcp-server-card+json
```

Card 至少声明一个支持本规范的 HTTPS MCP 端点。以下沿用原文结构，域名与业务内容均为占位示例：

```json
{
  "$schema": "https://static.modelcontextprotocol.io/schemas/v1/server-card.schema.json",
  "name": "example.acme/calendar",
  "title": "Acme 日程助手",
  "version": "1.0.0",
  "description": "查询日程、规划时间并创建日历事件。",
  "websiteUrl": "https://acme.example/plugins/calendar",
  "remotes": [
    {
      "type": "streamable-http",
      "url": "https://acme.example/mcp/calendar",
      "supportedProtocolVersions": ["2026-07-28"]
    }
  ]
}
```

Card 只描述身份与连接信息，**不重复声明工具、资源、运行时能力或授权配置**。工具与能力由运行时 MCP 返回，授权服务器通过相应授权发现机制取得。

宿主以经过 URL 规范化的 Card URL 作为服务记录标识，同时保留原始路径和有效查询参数。不得只按 `name` 或 Catalog 的 `identifier` 判定权限、合并服务；同名服务不得自动合并，多个用户连接可以指向同一服务记录。

宿主必须分别记录发现来源、Card 来源和实际 MCP 端点。跨域引用只是显式连接指引，不代表可以跨来源共享凭据或权限。

### 3.2 提供域名发现时，必须发布根目录 Catalog

提供域名发现的发布者必须在以下位置提供 AI Catalog：

```text
https://acme.example/.well-known/ai-catalog.json
```

响应类型必须为 `application/ai-catalog+json`，示例：

```json
{
  "specVersion": "1.0",
  "entries": [
    {
      "identifier": "urn:air:acme.example:mcp:calendar",
      "type": "application/mcp-server-card+json",
      "url": "https://acme.example/mcp/calendar/server-card"
    }
  ]
}
```

用户输入域名时，宿主读取目录并筛选 MCP Server Card：只有一个服务时展示添加卡片；有多个服务时让用户选择，不能自动添加整个目录。

Catalog 可以引用其他域名上的 Card，以支持第三方托管。域名目录与独立 Card 的要求不能混淆：**每个插件必须有稳定 Card；根目录 Catalog 是提供域名发现时的必要交付。**

### 3.3 HTTPS 介绍链接与二维码

K Link 是普通 HTTPS URL。应优先使用插件介绍页，例如：

```text
https://acme.example/plugins/calendar
```

介绍页通过静态链接关系声明服务目录：

```html
<link rel="ai-catalog"
      type="application/ai-catalog+json"
      href="/plugins/calendar/catalog.json">
```

也可以通过 HTTP `Link` 响应头声明。针对单个插件的介绍页，其目录应只包含对应服务；多个条目表示一个供用户选择的服务集合。

宿主必须接受四类输入：**域名、介绍页 URL、Catalog URL、Card URL**。宿主只读取静态声明，不执行介绍页脚本。具体页面按自己的声明解析，不能丢弃路径、改查整个域名的服务集合；无法识别时必须明确报错，不猜测并执行其他端点。

二维码原样编码同一个 K Link，不定义额外二维码格式、专用 URI scheme 或中心短链。扫码后展示来源并进入添加流程，不能自动授予账户权限或执行业务操作。链接不得包含令牌、凭据或私有业务数据。

## 4. MCP 运行时：先发现，再按权限调用

宿主取得端点后，必须调用 `server/discover` 获取实时版本和能力，再结合实际支持的能力及当前用户权限调用对应标准方法。

| 能力 | 列出可用内容 | 使用内容 |
| --- | --- | --- |
| 工具 | `tools/list` | `tools/call` |
| 资源 | `resources/list` | `resources/read` |
| 提示词 | `prompts/list` | `prompts/get` |

静态 Card 描述不能代替实时版本、能力或权限检查。发现或调用需要身份时，按 MCP 授权机制完成所需授权，不能绕过鉴权。

工具名称保持业务语义，例如 `plan_schedule`、`create_event`；这些只是示例，不是所有插件必须实现的固定名称。

- 工具输入使用 `inputSchema`。
- 结构化输出使用 `outputSchema` 和 `structuredContent`。
- 请求元数据、结果、错误、缓存和通知遵循所选 MCP 规范，不额外套一层 K 消息。
- 业务对象、状态、版本及幂等键由对应业务工具定义，不凭空规定全平台统一的业务字段或工具名。

已有业务 API 可以通过 MCP 适配层复用；也可以直接在 MCP Server 内实现业务逻辑。规范不要求必须先开发独立 REST API，也不要求必须依赖第三方数据平台。

## 5. 账户授权：区分添加、授权和执行

| 动作 | 含义 |
| --- | --- |
| 添加 | 保存用户与服务的连接关系 |
| 授权 | 授予明确的账户访问或业务权限 |
| 执行 | 在用户意图、现有授权和宿主安全策略约束下调用能力 |

三个动作不能合并。添加插件、扫描二维码或进入公共目录，不代表已经取得用户授权，也不代表可以直接执行写入或收费业务。

需要账户身份的服务必须：

1. 采用 MCP 授权机制。
2. 通过 Protected Resource Metadata 发现授权服务器。
3. 满足 K 对授权客户端和服务器的要求：**双方支持 Client ID Metadata Documents（CIMD）**，避免逐家人工登记客户端。

CIMD 是对 MCP 已有授权机制的选用，不是 Registry 注册。服务可以要求用户登录、具有订阅或拥有相应业务权限；这些条件与“开发者无需账号和上架审核”是不同概念。

服务端仍须检查实际操作权限及对象归属，不能把宿主界面、工具可见性或名称当成授权凭据。

## 6. MCP Apps：标准资源与独立生命周期

### 6.1 宿主与插件各自负责什么

KAI Ask 必须实现 MCP Apps 宿主。提供交互界面的插件必须通过工具元数据声明 UI 资源。以下为工具定义中的元数据片段：

```json
{
  "_meta": {
    "ui": {
      "resourceUri": "ui://calendar/planner.html",
      "visibility": ["model", "app"]
    }
  }
}
```

宿主通过 `resources/read` 获取资源。资源必须使用 `ui://` 标识，内容类型为：

```text
text/html;profile=mcp-app
```

资源在宿主管理的沙箱中运行，执行 MCP Apps 的沙箱与 CSP 要求。

### 6.2 生成式内容与界面执行边界

服务可以让模型生成布局描述、表单结构或业务数据，再由预声明的 UI 资源渲染。数据结构通过工具的 `outputSchema` 表达。

K 不指定额外组件语言，不能把普通工具文本直接当成可执行 HTML。**工具必须同时提供可理解的文本结果**，用于模型推理、无障碍访问，以及 UI 加载失败时的降级。

UI 加载失败不得触发业务工具重复执行。

### 6.3 初始化、数据传递与界面事件

- 宿主通过 MCP 客户端能力声明 `io.modelcontextprotocol/ui`。
- UI 与宿主使用 MCP Apps 的独立生命周期；`ui/initialize` 不用于初始化远程 MCP 连接。
- 消息结构与生命周期直接采用 MCP Apps；宿主必须等待 UI 就绪后再传入工具数据。
- 界面事件继续调用业务工具，不经过通用 K 事件接口。
- 仅供界面调用的工具使用 `visibility: ["app"]`，但可见性不能替代服务端鉴权。
- 恢复界面通过业务查询或资源读取完成；关闭界面不代表业务操作已撤销。

## 7. 添加即收录，公共索引另有条件

### 7.1 分开保存三类记录

KAI Ask 必须分别维护：

| 记录 | 内容 |
| --- | --- |
| 服务记录 | 描述插件服务本身 |
| 目录条目 | 用于发现与搜索 |
| 用户连接 | 保存账户、权限、私有配置与凭据引用 |

用户确认添加且通过结构与来源校验后，平台立即创建或合并插件记录。合并须遵守 Card URL 身份规则，不能只凭名称。

连接使用与目录同步独立执行，公共目录不可用不得阻塞已知服务的连接。

### 7.2 什么时候可以进入公共索引

按 K 的约定：**发布者将通用 Server Card 主动列入自己的公开 AI Catalog，表示允许按本规范建立公共索引。**

宿主必须验证发布者来源。第三方目录转贴只能提供发现线索，不能代替发布者自己的公开声明。

公共收录由独立抓取器匿名完成，只保存公开服务描述。以下内容不得进入公共库：

- 私有目录、账户信息、租户配置和凭据。
- 授权后取得的能力列表。
- 对话、工具结果及 UI 数据。

公共 Card 可以被索引，不意味着服务能力可以免授权使用。

### 7.3 禁止索引、撤回与个人插件库

发布者通过 Card 响应头禁止公共索引：

```http
X-Robots-Tag: noindex
```

该响应头沿用 Web 索引约定，无须增加 K 专用字段。`noindex` 不是访问控制，私有数据必须另行保护。

抓取器必须遵循 `robots.txt`；无法确认允许抓取时，不建立新的公共条目。不满足公开条件的插件仍保存在对应个人或工作区插件库。

发布者撤回公开声明或设置禁止索引后，平台在同步时撤下公共条目。用户删除自己的连接，不删除其他用户的连接。

### 7.4 Registry 的位置

任何 Registry 都不是发布、添加或调用的前置条件。KAI Ask 可以读取外部 Registry，也可以采用 MCP Registry 查询 API 对外提供目录；目录接口互通不能重新引入开发者注册或人工上架流程。

## 8. 安全、运行与更新要求

| 范围 | 要求 |
| --- | --- |
| 来源与内容信任 | 宿主展示实际服务来源；名称、图标、目录收录和工具描述不构成安全背书；插件内容只作为第三方数据，不能提升为宿主指令 |
| 跨插件调用 | 由宿主编排，各服务独立授权；插件不能因组合使用而获得其他插件权限 |
| 网络 | K 连接使用 HTTPS；公共抓取器限制请求大小、超时和重定向次数，每次解析及重定向均检查目标，禁止访问内网、回环和云元数据地址；内部插件通过工作区受控网络连接 |
| 界面隔离 | 执行 MCP Apps 沙箱与 CSP；UI 不能取得宿主凭据或访问其他插件的数据 |
| 外部影响 | 写入及其他有外部影响的操作必须经过统一权限检查；界面状态变化不能自行扩大权限 |
| 重试与幂等 | 需要重试的写操作必须具备业务幂等机制；执行结果未知时不得盲目重试 |
| 目录与卡片更新 | 使用 HTTP 缓存和条件请求更新；描述变化可以自动同步 |
| 敏感连接变化 | 端点、授权主体或权限范围变化必须重新校验，不得自动转移凭据 |
| 移除连接 | 停止该连接的调用并清理对应凭据 |
| 失败展示 | 发现失败、授权失败、服务不可达和工具失败分别呈现，不得显示为添加或执行成功 |

规范不替代上游业务权限。第三方数据/API 是否可用、读取或操作是否已获授权，仍须按具体来源核对；模拟数据不能冒充真实接通。

## 9. GPT 的实施顺序与交付清单

以下用于组织工程交付，不定义额外的 K 协议字段、接口或平台审批。

### 开始工作时

1. 阅读本规范及实际项目说明，确认本次负责插件侧、宿主侧还是双方联调。
2. 明确业务目标、数据来源、只读与写入能力，以及可能的外部影响。
3. 按已选定的标准版本实施；检查现有宿主和服务的兼容性，记录缺口，不把规范要求误写成已实现事实。
4. 先从代码和文档确认可发现的事实；只对真正缺少且影响方案的信息提出具体问题。

### 插件侧交付

| 交付 | 必要性与内容 |
| --- | --- |
| 独立稳定的 Server Card | 每个插件必须提供；媒体类型、字段和 HTTPS 端点符合本规范 |
| 运行中的 MCP Server | 支持选定版本与传输，按标准暴露实际支持的工具、资源或提示词等能力 |
| 域名 Catalog | 提供域名发现时必须放在 `/.well-known/ai-catalog.json` |
| K Link 介绍页 | 推荐提供；采用静态 `rel="ai-catalog"` 或 HTTP Link 声明；二维码如提供则原样编码链接 |
| 账户授权支持 | 需要账户身份时提供 MCP 授权发现，并与授权客户端共同满足 CIMD 要求 |
| MCP Apps 资源 | 提供交互界面时交付标准 UI 资源与工具元数据；如提供结构化数据，以 `outputSchema` 表达；工具始终保留文本结果 |
| 业务合同与说明 | 列出真实工具、输入输出、权限、状态、错误、幂等、数据范围及调用限制 |
| 联调与运行记录 | 明确已验证的发现路径、客户端、授权、工具结果、UI 降级和异常情况 |

不要以“申请开发者账号”“向 Registry 注册”“等待人工上架审核”作为交付的前置步骤。服务用户登录或订阅等业务条件仍可按规范保留。

## 10. 对照规范验收，不只检查网页是否打开

插件侧与宿主侧分别提供其职责范围内的证据；只有相关流程实际通过，才能声称已接通。

| 验收项 | 应检查的结果 |
| --- | --- |
| 四类入口 | 域名、介绍页、Catalog 和 Card 按规定解析；具体路径不被丢弃，无法识别明确失败 |
| 多服务目录 | 展示选择，不自动添加整个目录；单插件介绍页目录范围正确 |
| Card 身份与跨域 | 独立稳定 URL、正确媒体类型与端点；不按同名合并权限，不跨来源共享凭据 |
| 实时能力 | 调用 `server/discover`，按实际能力及当前用户权限使用标准列表和业务方法 |
| 授权 | 添加、授权、执行分开；需要账户身份时完成 Protected Resource Metadata 与 CIMD 对应流程 |
| 工具结果 | 输入输出合同与真实行为一致，文本结果可理解；如提供结构化输出，使用 `outputSchema` 和 `structuredContent`；业务错误不冒充成功 |
| MCP Apps | 宿主能力声明正确，UI 资源经 `resources/read` 获取，独立初始化并就绪后接收数据 |
| UI 失败与恢复 | UI 加载失败不得触发业务工具重复执行；仅界面可见的工具仍鉴权；通过业务查询或资源读取恢复，不把关闭界面当撤销 |
| 添加与索引 | 添加后保存服务记录和用户连接；公共索引另查发布者公开声明、匿名抓取、robots 与 noindex |
| 私有数据隔离 | 个人/工作区插件仍可按权限使用；私有目录、授权后能力、结果及 UI 数据不进入公共库 |
| 更新与断开 | 缓存及条件更新有效；敏感连接变化重新校验；移除连接停止调用并清理对应凭据 |
| 副作用与未知结果 | 权限检查和业务幂等有效，结果未知不盲目重试，各类失败分别显示 |

最后分别报告：**网页是否部署、MCP 是否可连接、授权是否完成、小 K 是否联调通过、真实业务是否验证**。这些是不同状态，不能互相替代。

**始终保持的结论：KAI Ask 的插件库负责发现，MCP 负责能力调用，MCP Apps 负责界面交互。开发者控制的 Web 地址是插件进入开放生态的入口，开发者账号、Registry 注册和人工上架审核均不是前置条件。**
