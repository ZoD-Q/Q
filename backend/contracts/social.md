# Social API v1 — implementation contract

This module uses the existing Q Bearer session and UUID user IDs. `handle` remains the public Q handle. It is separate from AI conversations, plugins, video credentials and the simulated ledger. All responses (including errors) use `Cache-Control: no-store`. Times are ISO 8601 UTC; UUIDs are strings; sequence values are nonnegative safe integers. No end-to-end encryption or physical-erasure claim is made.

## Shared response shapes

- `SocialUser`: `{id,handle,display_name,avatar}`; no preferences, balance or credentials.
- `SocialFriend`: `{user,conversation_id,remark,muted,intimacy_enabled,peer_intimacy_enabled,intimacy_score,relationship_label,proposed_label,proposed_by,created_at}`. Labels are `close_friend|partner|couple|null`; proposed_by UUID or null. Own remark ≤40 chars. Score counts UTC days with ordinary messages sent in both directions while both users enable intimacy; one point maximum per day. No message text is analyzed. Disabling either side stops accumulation and clears that day's incomplete activity; reenabling does not backfill. Deletion/block ends this relationship generation; adding again creates a new conversation and zero score.
- `SocialRequest`: `{id,from_user,to_user,note,created_at}`. Only pending requests appear, note ≤80 chars.
- `SocialConversation`: `{id,user,last_seq,read_seq,peer_read_seq,unread_count,last_message,updated_at,active}`. `last_message` is a `SocialMessage|null` conversation preview: ordinary body is truncated to at most 160 Unicode characters; the messages endpoint returns its full body. Ephemeral body is always null, including after opening. Inactive historical conversations remain readable, but cannot send/open ephemeral messages; `active=false` after deleting a friend or blocking.
- `SocialMessage`: `{id,conversation_id,seq,sender_id,client_message_id,kind,body,ttl_seconds,opened_at,expires_at,unopened_expires_at,expired,created_at}`. kind `text|ephemeral`; ordinary body is text, ephemeral body is **always null** in lists, snapshots and send responses, even for its sender. TTL is `30|300|86400|null`. Metadata timestamps are nullable. `expired` also means ephemeral payload is unavailable (including restore from backups).
- `SocialNotification`: `{id,kind,user,created_at,read_at}`; kind `friend_request|friend_accepted|relationship_proposed|relationship_accepted`; no message text. Notifications are kept for 30 days, capped at 200 per user by deleting the oldest when inserting. This is an explicit bounded activity inbox, not an authoritative business record.
- `SocialMutation`: `{ok:true}`.

## Endpoints

All mutations derive the acting user from the session. `{}` is accepted where a JSON body is shown empty. Body objects reject unknown fields.

Use existing authenticated `GET /v1/users/lookup?handle=...` for exact Q-handle lookup. No public directory, phone-book upload, fuzzy search or stranger messaging is introduced.

## Bounded data and permissions

Snapshot returns every record in its bounded collections. Each user may have at most 200 active friends, 100 pending requests total across both directions, 500 historical conversations, and 200 blocked users. Exceeding a limit rejects the mutation with 409 `SOCIAL_CAPACITY` (never silently truncates snapshot collections). Notification retention/cap is stated above. Requests expire after 30 days. Message history is cursor-paginated with no implicit history truncation. Mutations have actor-scoped process-local limits: message send 60/minute; other social writes 30/minute; reads 240/minute. Repeated calls can return 429 `RATE_LIMITED`. These limits are not a distributed anti-abuse system.

Every two-user mutation locks both existing `identities` rows in ascending UUID order inside its transaction. Permission checks, friendship/block changes, sequence allocation and message commit happen after these locks. Sequence is allocated per conversation under this lock and committed with the message; no global serial/timestamp cursor. Unknown sender outcomes reuse the original client_message_id and payload. The ID is unique per sender across conversations. Changed conversation/body/TTL yields 409 `IDEMPOTENCY_CONFLICT`. An expired or missing ephemeral payload makes every send replay of its client_message_id return 410 SOCIAL_MESSAGE_EXPIRED, regardless of submitted text; content is never reconstructed. The by-client lookup remains available to recover the expired envelope without resending text.

Removing a friend or blocking preserves ordinary historical messages for both participants but disables new sends and intimacy; remaining ephemeral payloads in that relationship are deleted immediately. A block does not reveal which user blocked. Removing only one's block does not re-add a friend. Friend requests and relationship labels require explicit acceptance; mutual requests do not automatically accept. Report submission does not automatically block.

## Ephemeral messages and reports

A newly sent ephemeral payload is kept only in `social_ephemeral_payloads`, separate from its envelope. Unopened payload expires after 7 days. Opening is explicit, requires online receiving participant, and atomically fixes `opened_at` and `expires_at = opened_at + ttl_seconds`; every device/retry gets the same absolute deadline. Reading the conversation or marking read does not start it. Foreground clients use the bounded ephemeral-state endpoint for already-loaded/visible envelopes so another device opening or expiring an older message updates its metadata without moving the new-message after_seq cursor. After opening, TTL is independent of the initial 7-day unopened deadline. Unavailable/expired payload returns 410 `SOCIAL_MESSAGE_EXPIRED`. Sender never retrieves ephemeral body via this API. No notification or conversation preview contains ephemeral text. API reads enforce expiry immediately, independent of background cleanup.

The server's maintenance task runs every 30 seconds and on startup, removing up to 1000 expired payloads per pass (including any body-derived hashes), expired report evidence, expired requests and notifications. Logical expiry is immediate even if physical cleanup has a backlog. Expired envelopes remain as tombstones. Backup policy must exclude `social_ephemeral_payloads` data, including body-derived hashes; restoring a missing payload must not recreate it. Client caches/visible bodies and notification previews also need expiry cleanup. Screenshots, copied content and modified clients cannot be guaranteed erased.

When a report submission outcome is unknown, keep only its owner-scoped client_report_id as a local recovery pointer and query the by-client receipt endpoint; do not invent a fresh report ID or extend retention. A 404 means no receipt is currently committed and does not automatically authorize a new report. Reports use owner-scoped client_report_id idempotency: same payload returns 200 without new evidence or a new expiry; changed target/message/reason/include_evidence returns 409 IDEMPOTENCY_CONFLICT. Reports retain reason/target metadata for 30 days. After cleanup, only an owner-scoped client_report_id tombstone and original expiry remain; reuse returns 410 SOCIAL_REPORT_EXPIRED, so an old retry cannot start a new retention period. A message report must refer to a message sent by the reported user in the reporter's conversation. Evidence is copied only when include_evidence=true and message content is still available; ephemeral evidence additionally requires the reporter to have opened it and its deadline to remain live. An attempt to attach unopened ephemeral content is definitively refused with 403 SOCIAL_FORBIDDEN. Before returning that refusal, the transaction reserves a minimal owner/client_report_id receipt with an opaque report ID and a fixed original expiry, but no target, reason or body. GET and POST with that same client_report_id subsequently return 410 SOCIAL_REPORT_EXPIRED because no report was accepted, even if the message is later opened; an already-accepted receipt still takes precedence. Expired content is not recoverable for evidence. Evidence is in a separate restricted table `social_report_evidence`, has a fixed 30-day expiry from report creation (never extends on reads), has no public retrieval endpoint, and is excluded from normal messages/snapshots. No moderator interface exists in this increment. Backup policy must exclude `social_report_evidence` and `social_reports` data as well. Retain only the minimal `social_report_receipts` tombstone. After restore, a receipt with no report/evidence must not recreate evidence or metadata: reusing that client_report_id returns 410 SOCIAL_REPORT_EXPIRED even if its original absolute expiry is still in the future. Clients must disclose this 30-day evidence exception before submission.

## Errors and acceptance

Standard VALIDATION_ERROR (400), UNAUTHORIZED (401), RATE_LIMITED (429), INTERNAL_ERROR (500) retain their meanings. Social errors: SOCIAL_NOT_FOUND (404, including foreign resources), SOCIAL_FORBIDDEN (403), SOCIAL_BLOCKED (403), SOCIAL_FRIEND_REQUIRED (403), SOCIAL_ALREADY_FRIENDS (409), SOCIAL_REQUEST_PENDING (409), SOCIAL_REQUEST_CLOSED (409), SOCIAL_LABEL_PENDING (409), SOCIAL_CAPACITY (409), IDEMPOTENCY_CONFLICT (409), SOCIAL_MESSAGE_EXPIRED / SOCIAL_REPORT_EXPIRED (410). Self-targeting requests/blocks/reports are invalid.

Validate with two independently authenticated users and a third outsider: request acceptance/rejection/duplicate races, membership isolation, deletion/block/send races, concurrent sequence allocation and cursor completeness, same-key replay/conflict, monotonic read positions, unread counts, unopened/opened expiry and lost-open-response retries, no ephemeral leak in lists/notifications, independent per-message timers, missing-payload restore behavior, cleanup of payload/hash/report evidence, intimacy daily deduplication and disabled behavior, accepted labels, account-switch cleanup in clients. Native app lifecycle/screenshots and production multi-device push are separately unverified; this increment uses foreground polling every 3 seconds, no WebSocket or OS push.


The mobile conversation initially requests `latest=true&limit=100`, then explicitly prepends older pages via `before_seq`. The forward polling cursor is independent and advances only through fetched forward pages; sending or snapshot metadata never jumps it. Each catch-up pass is bounded to five pages and resumes at that cursor on the next poll. Older pages merge with current messages so concurrent polling cannot remove newly received messages. Loading history does not itself mark messages read. A visible loaded row advances the existing cumulative `through_seq` read position (including earlier history), never the snapshot's unfetched future position.
