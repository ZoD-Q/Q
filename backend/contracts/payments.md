# Q 钱包支付合同与恢复边界

核对日期：2026-11-05。本文描述当前源码；不代表服务器已部署、商户渠道已开放或真实资金已验收。机器可读合同为 [OpenAPI](openapi.json)；共享类型由合同生成，不能手工修改。汇率刷新见[版本与切换](../src/payments/FX.md)，真实操作员、退款与对账见[操作合同](payment-operations.md)。

## 范围与身份

本模块接受 CNY 付款，为独立 HKD 账本记账。QDC 与银行插件 HKD 仍是模拟资金，原表、余额和历史不参与这里的兑换或入账。真实 HKD 用户账户初始余额为零，没有欢迎金或演示充值回退。

客户与支付操作员均复用 Q 身份和 Bearer 会话。订单、报价与账本所有者来自服务端身份，不接收客户端指定的所有者。客户只能读取自己的订单和分录；普通客户没有支付审批权。提供操作员 UUID 不会创建账号或赋予第二套登录身份。

本模块不实现 KPS、真实账户间转账、银行出款或自动渠道退款。完整原路退款通过操作员工单、独立复审、外部执行凭证及不可变冲正处理；它不会调用七相退款接口。提现咨询页不构成提现命令。七相文档提供的其他 API 不自动成为 Q 的能力或调用授权。

## 接口索引

请求及响应字段、必填项和错误结构以 OpenAPI 为准。除回调与返回页外，以下路由均需 Q 登录；提案和审批还需相应操作员角色。

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| GET | /v1/payments/capabilities | 可用状态、渠道、限额、费用参数、时间及支持开关 |
| GET | /v1/payments/wallet | 当前所有者的独立 HKD 余额；账户尚无账本行时返回零 |
| POST | /v1/payments/quotes | 提交 channel 与 credit_amount_minor_hkd，返回冻结报价 |
| POST | /v1/payments/orders | 提交 quote_id 与 client_request_id，预留订单或恢复同一请求 |
| GET | /v1/payments/orders | view=pending/history、limit、cursor 分页 |
| GET | /v1/payments/orders/active | 当前客户端可恢复的单一收银台槽位 |
| GET | /v1/payments/orders/by-client-key/{key} | 查询原请求，不创建新的供应商订单 |
| GET | /v1/payments/orders/{id} | 当前所有者的原始订单结果 |
| POST | /v1/payments/orders/{id}/detach | 明确确认旧付款仍可能完成后解除收银台关联 |
| POST | /v1/payments/orders/{id}/proposals | maker 对指定证据版本提出入账提案 |
| POST | /v1/payments/orders/{id}/approvals | 不同 checker 审核同一提案与证据版本 |
| GET | /v1/payments/ledger | 当前所有者的 HKD 入账分录分页 |
| GET | /v1/payments/qixiang/notify | 七相签名通知；成功响应为纯文本 success |
| GET | /v1/payments/return | 仅提示返回 Q 查询；不改变付款或入账结果 |

13 个路径不等于 13 次业务调用；orders 路径同时包含 GET 与 POST。业务 JSON 禁止未知字段；支付路由请求体上限 16 KiB，通知另有原始参数长度和字段数限制。分页 limit 为 1–50，默认 20；游标是时间与 UUID 的组合，不能自行改写成页码。

所有金融金额使用整数最小单位：100 HKD cents = HK$1.00，100 CNY cents = ¥1.00。正数金额不得超过 9007199254740991，费用允许为零。客户端额外校验安全整数、币种以及 base_amount_minor_cny + fee_minor_cny = pay_amount_minor_cny，显示金额也采用整数运算。缺失能力配置时，限额等字段可以为 null；不能把 null 解读为零额度或无限额度。

channel 使用 wechat/alipay；供应商适配内部映射为 wxpay/alipay。当前独立多订单模式关闭；旧订单可以通过明确 detach 让出收银台槽位，但仍保留其核实义务。客户端不能仅按状态名称决定可新建付款，应同时读取 terminal、safe_to_start_new、can_detach_checkout 和 checkout_detached。

## 报价与配置

配置完整格式见 [操作员说明](../src/payments/README.md)。所有费用、额度、时间与操作员均需明确配置，没有 KAI 费率默认值或默认商户。缺省手工汇率；显式 `Q_PAYMENT_FX_AUTO_REFRESH=1` 才启用固定 ECB 资料的版本化采集、证据留存和失效规则。配置由可信服务端运维提供，不能由客户端或供应商回调覆盖。

推荐使用 Q_PAYMENT_CREDENTIALS_JSON 和 Q_PAYMENT_ACTIVE_CREDENTIAL_VERSION 管理最多 32 个凭据版本，并配置 Q_PAYMENT_POLICY_JSON。兼容的单凭据环境形式也必须提供明确版本。商户密钥只存在服务端秘密配置，不进入客户端、订单数据库、URL、日志、截图或合同示例。版本名称是非秘密引用；版本所指商户和密钥不得被静默替换。

报价保存来源 URL、来源日期、源时间、获取时间和证据 SHA256。手工配置的快照仍需独立核验，字段或哈希存在不证明已在线核验；自动快照保留实际下载的原 XML 与服务器计算的 SHA256。源日期不因重启、304或重复下载而续期。来源失效会阻止新报价；原报价在其有效期和安全策略允许范围内保持原值，原订单继续按冻结内容恢复。

汇率与业务政策分开版本管理：普通汇率更新不使300秒内的旧报价失效；费用、额度、凭据和权限等业务政策变化仍有校验。首次升级可按原报价的冻结汇率重建旧指纹进行兼容；不重写原报价或订单。

新报价和新订单要求付款人之外的两位不同且活跃的审核员；不满足时返回 `PAYMENT_REVIEWERS_UNAVAILABLE`。在创建事务内按 UUID 顺序锁定付款人与审核员，并核对当前数据库角色策略，使停用和角色更新不能越过入单时的检查。原订单回放及过期未创建回执不受这一新收款门槛阻断。

设 R 为明确配置的“每 100 HKD 对应 CNY”十进制，bps 为用户费用基点，H 为 HKD 最小单位金额：

~~~text
base = ceil(H × R / 100)
pay  = ceil(H × R × (10000 + bps) / (100 × 10000))
fee  = pay - base
~~~

使用 checked i128 有理数计算，再检查输出范围。total_ceiling_minor_v1 是 Q 的实现政策，不能据此声称恢复了 KAI 后台收费算法。报价、费用、来源和其配置指纹不可修改；quote_id 单次使用，即使其最终产生的只是未创建回执。

供应商 endtime 支持带时区 RFC3339；旧式年月日时分秒只有在明确配置固定时区偏移后才解析。缺失、无法确定、未来或不在订单支付窗口内的时间进入 review_required。浏览器返回时间、通知到达时间和查单时间均不能替代付款时间。没有普通审批接口可以猜测、修改或绕过这份证据。

## 创建、幂等和中断

1. 服务端在事务内锁定当前身份，按所有者和 client_request_id 查找原订单。同一键和 quote_id 返回原结果；复用键更换报价返回冲突。
2. 对新请求校验本人报价、单次使用、报价时效、配置指纹及收银台槽位。槽位由数据库主键约束，不能依赖 UI 检查防并发。
3. 先提交订单、唯一商户订单号与持久工作项；工作者在网络创建前持久标记 may_have_sent_at。网络调用不持有数据库事务。
4. 每个可能已发送的请求只查原商户订单号。超时、取消、崩溃和查无结果均不能授权另建供应商请求。
5. 工作项使用 epoch、随机 token、租约截止时间和捕获的订单版本。结果提交再次加锁并核对，过期或旧版本结果不能覆盖新证据或已入账状态。

客户端先保存不含令牌的原请求，再向 Q 提交。原键查询返回结构化 PAYMENT_NOT_FOUND 时，客户端可重放同一个 Q 幂等命令；这与自动重发不确定的供应商写入不同。普通 404 页面、不支持的端点、401、429 或网络未知结果不能授权换键。

**过期报价但从未预留订单**：Q 持有身份锁，确认原键没有订单且报价未被另一订单使用后，保存 failed/not_created 的终态回执。它沿用原报价、商户和凭据版本，不创建工作项、槽位或分录；原键之后始终返回该回执。即使当前支付配置不可用，这种原键恢复仍可执行。客户端接受匹配回执后才清除自己的 pending，不能仅因本地过期判断或 HTTP 错误而丢弃意图。

## 通知、查单和状态

适配依据为 [七相旧版文档](https://qixiangpay.cn/doc_old.html)。接收端先只解析一次原始参数，拒绝未知字段、解码后重名、损坏编码、无效 UTF-8 和歧义编码。字段集合限定为 pid、trade_no、out_trade_no、type、name、money、trade_status、sign、sign_type，以及可选 param。

MD5 按参数名 ASCII 排序；仅排除 sign、sign_type 和空值，保留字符串“0”，不修剪值，不先对签名值进行 URL 编码。通知选择订单保存的凭据版本，核对商户、渠道、原商户单号、已绑定供应商单号和精确 CNY 金额；未知订单或不匹配通知不入队，也不返回 success。

只有通知与去重工作项持久成功后才确认收到。重复通知不改变已有查询退避或租约。验签成功仅是通知，不是支付凭证；工作者通过服务端 POST 表单查单，密钥不进入 URL。运输层限制超时和响应大小，禁止重定向及自动请求重试，错误和日志不包含密钥或原始供应商正文。

| 状态/条件 | 含义与允许行为 |
| --- | --- |
| creating / confirming | 创建或结果待核实；保留原键，不换单猜测结果 |
| awaiting_payment | 仅在链接存在、未到期且未 detach 时显式打开收银台 |
| awaiting_credit_approval | 已匹配供应商付款证据，HKD 尚未计入余额 |
| crediting / credited | 状态词汇支持；实际余额以服务端已提交账本为准 |
| expired | 收银台窗口过期，不能据此推断未扣款或不再查单 |
| review_required | 证据、账户或配置需要处理；不能当作付款失败 |
| failed + not_created + terminal | 有持久证据证明未创建，不存在供应商资金义务 |

这张表描述 Q 的实现，不是已验证的供应商状态迁移图。detach 不撤销付款、不退款、不证明未扣款。可能已发送的旧订单继续查询；供应商凭据暂缺时显式保留待核实状态，并优先处理可用版本的其他工作，避免旧任务堵塞新订单。

## 审批、账本和账号生命周期

已匹配且时间有效的付款先等待 maker 提案，再由另一名 checker 审核。双方与客户必须仍为现有 active Q 身份；角色来自可信服务端配置。审批核对证据版本、哈希与不可变提案，不能由客户提供“支付成功”布尔值替代。

锁顺序是身份 UUID 排序 → 订单 → 收银台槽位 → HKD 账户 UUID 排序。工作项在身份、订单与槽位的同一围栏内操作。实际入账在一个 PostgreSQL 事务内写审批记录、唯一 payment_id 交易、清算/用户成对分录、缓存余额及 credited 订单。用户不得透支；独立清算对手账户可为负。数据库约束检查账户归属、借贷平衡、缓存余额和原付款/审批关联，历史分录不可编辑或删除。

真实余额非零或存在任何 unresolved 订单时拒绝客户及管理员删除。包括可能已发送的到期、detach、未知结果、待审批和人工核实订单。只有在身份、订单、槽位和工作项锁下证实从未设置 may_have_sent_at 的取消，才可产生 not_created、移除槽位与工作项，使零余额账号恢复删除资格。暂停账号保留付款证据并阻止普通入账审批，不抹除义务或历史。

完整退款支持冻结可用余额、双审、外部结果未知保留、错误退款凭证退回补正及原交易关联冲正。旧凭证永久保留，新凭证只追加；复审绑定最新版本和哈希。没有自动渠道退款、提现或人工改写原付款证据的接口。

用户余额扩展为总额、退款冻结和可用金额；分录可包含明确标为 `refund_reversal` 的负数冲正。订单保留原支付状态并附退款编号、状态、版本和完成时间。客户端须分别展示付款与退款，不能把历史入账描述成当前可用资金。

兼容边界：旧报价和原订单恢复继续可用；只接受正数入账分录或不认识退款附加字段的旧客户端，需要更新后才能完整展示退款与负分录。服务端余额仍是最终事实，不得为迎合旧界面隐藏冲正或把旧入账再计一次。新后台操作员功能也需要本轮 Web 与 API 配套部署。

支付及退款对账比较原冻结 CNY 金额，银行结算材料与 HKD 储备材料分别记录。`operator_verified` 仅表示不同操作员复核了原文件及映射，不证明银行 API 已认证、港币已购入或真实清算已验收。真实结算须另核外部流水；详见[操作合同](payment-operations.md)。

## 验证界限

单元与回环 HTTP 替身覆盖签名、金额、通知、查单和运输边界。独立 PostgreSQL 测试覆盖幂等、租约、并发审批、凭据版本、未发送取消、过期报价终态回执、账本与删除围栏；这些是本地功能证据，不是供应商或业务数据库验收。测试入口和隔离要求见操作员说明及仓库 AGENTS.md。完整回归、两端最新提交 CI、PR/MR 和原生平台状态由最终集成记录填写；本文不宣称尚未执行的检查已通过。
